> Camera-guided cube solving, learning, and speedcubing web app. Production domain: **solvepath.app**

## 0. How to work on this project

You are building a production-quality, open-source web app from scratch. **The goal of this project is a finished, polished, working app.** A YouTube "build this with me" guide will be created later, in a separate effort, only after the app is done and proven worth showing (see Section 12). Do not shape the build around video episodes or viewer pacing. Do keep the code readable and well-structured, because it will later be explained to an audience of parents.

Working rules:

1. **Plan first.** Read this whole document, then produce `docs/PLAN.md` with architecture, library choices (verified versions and licenses), data model, and the milestone breakdown in Section 10. Stop and wait for my approval.
2. **Create `CLAUDE.md`** in the repo root with conventions, commands (dev, test, build, deploy), and the current milestone. Keep it updated.
3. **One milestone at a time.** Each ends with passing tests, a working build, a `docs/milestones/MXX.md` changelog, and a git commit. Do not start the next milestone until I confirm.
4. **Keep a lessons-learned log** in `docs/LESSONS.md`, updated at the end of every milestone: what worked, dead ends and why they failed, bugs that took the longest, decisions that changed, prompts or instructions that produced good or bad results, and anything a person rebuilding this from scratch should do differently. This log is the raw material for the later YouTube guide, so be candid and specific.
5. **Verify, don't assume.** Before adopting a library, check its current version, license, maintenance status, and browser support. Pin exact versions. If anything in this document is wrong or outdated, say so and propose a fix.
6. **Never invent cube algorithms.** Every named algorithm in the data files (OLL, PLL, F2L, CMLL, beginner steps, patterns) must be machine-verified by a test that applies it to the cube model and confirms it does exactly what its name and case ID claim. A mistyped or made-up algorithm is the most likely silent bug in this project.
7. **Every cube state the app creates must come from a solved cube via legal moves.** Scrambles, patterns, practice positions, trainer cases, and test fixtures are generated by applying move sequences to solved, never by editing stickers. This guarantees every generated state is physically reachable and solvable by any method.
8. **Free to build and run.** No paid services, no API keys, no paid tiers, no ads, no analytics or trackers. Everything open source. Fonts and assets self-hosted.
9. **Ask before** adding any dependency that is not open source, collecting any new personal data, or changing the auth or privacy model.
10. **Writing style for UI copy and docs:** plain, friendly, readable by a 10-year-old. Never use em dashes.
11. **Name and trademark:** do not use "Rubik's" in the app name, logo, domain, or branding. Descriptive phrases like "works with any 3x3 puzzle cube" are fine. The app name is **SolvePath** and the production domain is **solvepath.app**. Keep both in one config module so they can be changed in one place.

## 1. Product summary

A zero-install, cross-platform web app for families. Parents set it up; kids and parents use it to learn, solve, and speedcube.

1. **Scan:** the camera reads a physical 3x3 cube while the user slowly spins it using a taught grip. Supports cubes with non-standard colors.
2. **Choose a goal:** solved, or one of many patterns (checkerboard, superflip, cube-in-cube, etc.).
3. **Choose a method:** Shortest, Beginner (layer-by-layer), 2-Look CFOP, Full CFOP, Roux, ZZ.
4. **Follow along:** a 3D cube on screen shows the cube from the user's own point of view, highlights the face to turn, and animates the direction. The user steps through moves at their own pace.
5. **Rescan to sync:** a "Rescan" button is always on screen. Rescanning compares the real cube to where the app expects it to be, then continues, jumps to the right step, explains a mistake, or re-plans.
6. **Learning Center:** step-by-step courses for each method, drills that isolate one stage, algorithm trainers, a "Next move?" quiz, and a Coach that recommends what to practice next.
7. **Speedcubing timer** comparable to csTimer: spacebar and touch, inspection, penalties, averages, sessions, stats, scrambles.
8. **Practice positions:** the user applies a listed sequence to a solved cube, the camera confirms the result, then they solve from there.
9. **Accounts, achievements, leaderboards, themes**, all family-safe.
10. **Built-in Guide:** every feature, setting, and stat is documented, and clicking any feature or setting title opens its Guide entry.

## 2. Hard constraints

- **No download required.** Runs in modern browsers on Windows, macOS, Linux, ChromeOS, Android, iOS/iPadOS. Installable as a PWA as an option, never required.
- **Camera frames are processed in memory and discarded.** Video is never recorded, stored, or uploaded. It exists only so the software can read the cube. Say so clearly in the UI.
- **Low-end hardware is the performance target**, specifically school Chromebooks and older iPads. Camera preview at 30 fps, vision processing at 10-15 Hz in a Web Worker, and the main thread is never blocked by solver or CV work.
- **Secure context:** `getUserMedia` requires HTTPS (localhost is exempt). Local dev must support HTTPS for testing phones over the LAN.
- **Two deployment modes, both free:**
  - **Local-only mode:** the static build works with no backend at all (guest profiles, all data in the browser). Deployable to free static hosting (GitHub Pages, Cloudflare Pages).
  - **Full mode:** adds accounts, cloud sync, and leaderboards via a self-hosted backend in Docker Compose.
- **Licenses:** cubing.js is dual MPL-2.0 / GPL-3.0-or-later as of my last check. Verify, and choose a compatible license for this repo.
- **Version pinning everywhere:** exact npm versions with lockfile; Docker images pinned by tag and digest.

## 4. Architecture

Monorepo with clean module boundaries so each piece is testable alone:

```
apps/web/                 # React app
packages/cube-core/       # Cube model, notation, moves, orientation, point-of-view transforms, group math
packages/solvers/         # Two-phase wrapper, Beginner, CFOP, Roux, ZZ, pattern solving, stage detection
packages/vision/          # Grip/scan tracking, face detection, color clustering, mark detection, validation
packages/algs/            # Verified algorithm, pattern, and practice-position data (JSON) + verification tests
packages/timer/           # Timer state machine, inspection, penalties, averages, stats, phases
packages/learning/        # Courses, drills, case generation, spaced repetition, Coach rules
packages/achievements/    # Data-driven achievement rules (shared by client and server)
packages/sources/         # Input-source interfaces (scan, manual, virtual cube, future smart cube)
server/                   # PocketBase config, migrations, pb_hooks (JS), seed data
deploy/                   # docker-compose.yml, Caddyfile, healthchecks, admin landing page
docs/                     # PLAN.md, milestones, guide/ (user-facing documentation)
```

**cube-core is the source of truth.** Vision produces observations, solvers produce move sequences, the renderer displays state, and all of them use cube-core's types.

## 5. Feature specifications

### 5.1 Cube model and notation (`cube-core`)

- Facelet and cubie representations with lossless conversion. Singmaster notation: face turns (U D L R F B with ' and 2), wide moves (u or Uw), slices (M E S), rotations (x y z).
- Explicit, documented composition convention. Inverse, compose, and relative-state helpers.
- Validity checks with specific diagnoses: sticker counts, valid pieces, corner twist sum, edge flip sum, permutation parity. Return which check failed and the likely offending stickers or pieces.
- **Color scheme abstraction:** logical faces (U D L R F B) are separate from physical colors. A cube profile maps 6 physical colors (with user-editable names) to faces. This is what makes non-standard colors work everywhere.
- **Orientation from centers:** compute whole-cube orientation (24 possibilities) from visible centers.
- **Point-of-view transform:** the face pointing toward the user faces away from the camera. All instructions and the 3D view are expressed in the user's frame (F = the face toward the user's eyes), never the camera's frame. Make this transform a single tested function used everywhere.

### 5.2 Camera scanning (`vision`)

**Grip and scan technique (taught in a short animated lesson on first use, replayable any time):**
- **Grip:** pinch the cube between thumb and fingertip on the **top and bottom center stickers**, about 30-50 cm from the camera. Fingers then cover only centers, and center colors can be inferred from the color scheme and neighboring pieces. Do not grip by corners or edges: covered corner and edge stickers cannot always be inferred (two hidden corners leave 3 possible cube states).
- **Spin:** with the chosen top color up, slowly spin the cube one full turn around the vertical axis (about 5 seconds), so the camera sees all 4 side faces. Then tip the top toward the camera, then the bottom.
- **Continuous tracking during the spin:** the scanner follows the cube between faces, so it learns how faces connect to each other from the motion itself. The user doesn't need to present faces in a perfect order.
- **Live coaching:** short prompts ("Slower", "A bit closer", "More light please", "Got it!") and a mini 3D cube that fills in each face as it's captured, with a 6-face progress ring.
- Auto-capture when a face is stable and confidently detected. A satisfying capture animation.

**Setting the starting orientation:** after the scan, tell the user exactly how to hold the cube using their cube profile's color names: "Hold it with **white** on top and **green** facing **you**." Show the matching 3D cube from the user's point of view.

**Left/right calibration:**
- Raw `getUserMedia` frames are not mirrored by the browser; mirroring is only a display choice. But some cameras, drivers, and virtual cameras (OBS Virtual Camera, some webcam utilities) flip the feed. So run a **one-time calibration per camera**: "Hold the cube up, then move it to your right" with a 3-second on-screen countdown. Track the cube's position across the countdown to learn which image direction is the user's right. Store the result per camera `deviceId`. Re-run from Settings.
- Separate **"Mirror camera preview"** display toggle (default on, so it behaves like a mirror). Processing always uses the calibrated orientation, regardless of how the preview is shown.

**Color classification (must support non-standard colors):**
- Sample each sticker as a robust median over an inner patch, in OKLab or CIELAB.
- Use the 6 centers as cluster seeds and assign all 54 stickers with a **balanced assignment** (exactly 9 per color) using the Hungarian algorithm or constrained k-means, not fixed color thresholds.
- Per-session white balance correction and glare rejection.
- Save each cube's colors to a named **cube profile** ("My blue-and-pink cube") to make rescans faster and more accurate.

**Escalation for hard-to-read cubes (in order):**
1. Lighting coach: detect dim, backlit, or warm-tinted frames and suggest fixes (face a window, avoid a lamp behind you).
2. Tap-to-fix: highlight the lowest-confidence stickers and let the user tap to correct them. Mandatory feature.
3. **Marking mode:** if two colors stay confused across scans, ask the user to mark **all 9 stickers of one of the two confused colors** with a removable mark (a small dot of painter's tape or a removable sticker dot; warn that ink may stain). It has to be one color, not one face, because a scrambled cube spreads each color across several faces. The app then detects the mark inside each sticker and uses it to tell the two colors apart. Save "marked" in the cube profile.
4. Manual entry: a 2D net editor.

**Validation results in plain words:**
- Likely misread: "We might have read these 2 stickers wrong. Tap to check them."
- Physically impossible state (twisted corner, flipped edge, or swapped pieces): "One corner looks twisted. This can happen if a cube pops apart. Here's how to fix it." Link to a Guide page on reassembling a popped cube.

### 5.3 Guided solving: Scan, Follow, Rescan

The camera does **not** watch every move. The app scans to learn the state, the user follows on-screen steps, and a rescan resyncs whenever needed. This is more reliable than live move tracking on low-end hardware, where hands block the view.

- **Follow:** after the scan, the app computes the solution. The user steps through it with Next/Back (tap, spacebar, or arrow keys) or an optional auto-advance tempo. The 3D cube shows the expected state from the user's point of view, highlights the face to turn, shows an animated arrow, and gives a plain-language label ("Turn the right side up, away from you") plus notation (R) for learners. Show the current stage (for CFOP: Cross > F2L 2/4 > OLL > PLL).
- **Rescan button**, always visible (plus a keyboard shortcut). A rescan returns the real state; compare it to the expected state at the current step:
  - Matches the current step: "You're right on track."
  - Matches a nearby step (the user went ahead or fell behind): jump to that step.
  - Matches the expected state plus a small mistake (search up to 3 moves): explain it ("Looks like the last turn went the wrong way. Turn the right side twice to fix it.") and offer Fix or Re-plan.
  - Anything else: re-plan from the scanned state with the same goal and method. For human methods, detect which stages are already complete and resume at the right one.
- **Quick check:** a one-face scan of the face toward the camera, compared against the expected state. Takes about 2 seconds. Suggest it at stage boundaries (after the cross, after F2L).
- **Input sources:** define `StateSource` and `MoveSource` interfaces in `packages/sources` with implementations for camera scan, manual net entry, and the virtual cube. **Bluetooth smart cubes: hooks only.** Define the interface, a stub, and a disabled feature flag, plus a short doc on how to add it later. Do not write any vendor Bluetooth code in this build.
- **Virtual cube mode:** a fully playable on-screen cube with csTimer-style keyboard controls and touch swipes, for users without a camera, for practice, and for demos.

### 5.4 Solvers (`solvers`)

All solvers run in a Web Worker. Cache pruning tables in IndexedDB and show progress the first time they are generated.

| Method | Implementation approach | Notes |
|---|---|---|
| Shortest | Kociemba two-phase, time-bounded (best found within about 1-2 s on a Chromebook) | Label it "Shortest found", not "optimal", unless proven optimal |
| Beginner (layer-by-layer) | Stages: white cross, white corners, middle edges, yellow cross, yellow edges, position yellow corners, orient yellow corners | The starting point for new solvers |
| 2-Look CFOP | Cross via IDA* (8 moves max), F2L via restricted search plus case lookup, 2-look OLL (10 algs) and 2-look PLL (6 algs) | Bridge from Beginner to CFOP |
| Full CFOP | Same cross and F2L, full OLL (57) and full PLL (21) case tables with AUF handling | |
| Roux | First and second blocks via restricted IDA*, CMLL case table, LSE via search | |
| ZZ | EOLine via search, F2L with R/U/L moves, OCLL + PLL | |

**Pattern goals:** to go from current state S to target pattern T, compute the relative state (T inverse composed with S, per the documented convention), solve it with the two-phase solver, and apply the result. Property test: for random S and every pattern T, applying the result to S gives exactly T. For human methods, solve to solved first, then append the pattern's sequence as a clearly labeled second phase.

**Stage detection:** a function that reports which stages of a given method are already complete for any state. Used by rescans, re-planning, drills, and the Coach.

**Output format:** an ordered list of stages, each with name, purpose, moves, and algorithm IDs. This feeds guidance, teaching, and stats.

### 5.5 Patterns library

At least: Checkerboard, Superflip, Cube in a Cube, Cube in a Cube in a Cube, Six Spots, Four Spots, Cross, Plus/Minus, Wire, Python, Tetris, Anaconda, Vertical Stripes, Twisted Rings, Exchanged Peaks. Each has a name, a thumbnail rendered from its state, a difficulty tag, and a generator sequence from solved (Working Rule 7), with a test that confirms the state.

### 5.6 Practice positions

A library of positions defined as sequences applied to a solved cube ("T-Perm practice", "OLL 27", "Easy 5-move scramble", "Superflip"). Flow: the camera confirms the cube is solved, the app guides the setup moves, the camera confirms the result, then the user solves from there, guided or unguided. This is also the engine for drills and trainers.

### 5.7 Learning Center (`learning`)

A clear, dedicated section of the app. Methods are learned in steps, and any step can be practiced on its own.

**Learn (courses):**
- Suggested path: **Beginner** (layer-by-layer) > **2-Look CFOP** > **Full CFOP**. **Roux** and **ZZ** are alternative paths after Beginner. Explain in the Guide why Beginner comes first and which Beginner skills carry into CFOP.
- Each method is split into lessons, one per stage. Each lesson: the goal in one sentence, a short 3D animation, worked examples on the virtual cube, then practice on the real cube via practice positions.
- Notation lesson first: interactive tutorial for R, U, F, primes, and doubles on the virtual cube.
- Progress tracking per lesson and per method.

**Practice (stage drills):**
- Drill any single stage in isolation: "just the cross", "just F2L pair 1", "just OLL", "just PLL", "just the Roux second block".
- Generate drill states that have every earlier stage solved and the target stage randomized, built from solved via legal moves (Working Rule 7). Verify with stage detection.
- Track time and success per drill.

**Algorithms:**
- Each algorithm has an ID, a name (Sune, T-Perm, etc.), tags, and "also used in" links. When an algorithm appears in a lesson or a guided solve, show "You'll see this one again in...". Track how often the user has run each algorithm.
- "My algorithms" page: per case, pick a preferred algorithm from verified alternatives.
- Recognition trainer (see a case, name it) and execution trainer (set up a case via practice positions, solve it, timed). Spaced repetition prioritizes slow or missed cases. Progress views: "You know 6 of 21 PLLs."

**"Next move?" quiz:** show a cube state from a lesson the user has started and ask what comes next (multiple choice, with the 3D cube animating each answer when chosen). Wrong answers link to the right lesson. Results feed the Coach.

**Coach ("What should I work on next?"):** a transparent, rules-based recommender (no AI service) that looks at lesson progress, drill and trainer results, quiz results, and timer phase splits, then suggests 1 to 3 next steps, each with a reason and a one-tap start. Example: "Your F2L takes over half your solve time. Try the F2L pair drill." Show the reasoning so parents and kids can trust it.

### 5.8 Speedcubing timer (`timer`)

Match the core of csTimer, with every item documented in the Guide (Section 5.12):

- **Start/stop:** spacebar hold-to-arm (configurable hold, default 0.3 s, timer turns green when armed), release to start, any key to stop. Touch equivalent: hold anywhere on the timer area. Prevent page scroll and focus problems.
- **WCA-style inspection:** optional 15 s with audio and visual callouts at 8 s and 12 s, automatic +2 at 15-17 s, DNF after 17 s.
- **Penalties:** OK, +2, DNF, editable afterward. Delete with undo.
- **Scrambles:** random-state 3x3 scrambles from `cubing/scramble` with 2D net and 3D previews. "Easy" short scrambles for beginners.
- **Statistics:** best single, mo3, ao5, ao12, ao50, ao100, ao1000 using WCA trimming rules (including DNF handling), session mean, standard deviation, solve count, PB history, time-series chart.
- **Sessions:** multiple named sessions; move solves between them.
- **Phases (multi-phase timing):** optional. The user presses the spacebar (or taps) at the end of each stage to record splits, for example Cross, F2L, OLL, PLL. Stored per solve, used by the Coach.
- **Method tag:** each solve records which method the user used (for achievements and the Coach).
- **Import/export:** JSON export of all data; import from csTimer's export format.
- **Focus mode:** only the timer is visible during a solve.

### 5.9 Accounts and family safety

The app is set up by parents but used by kids, so design for minimal data. In the US, COPPA governs collecting personal information from children under 13; the UK Age Appropriate Design Code and GDPR also apply to UK and EU users. Flag anything that needs legal review; I will have a lawyer review before a public launch.

- **Guest mode first:** everything except cloud sync and leaderboards works with no account, stored locally. Guest data can be moved into an account later.
- **Parent account** (email + password, passkeys, or OAuth through PocketBase). Parents create and manage **player profiles**.
- **Player profiles collect no personal information:** no email, real name, birthday, photo, or free text.
- **Display name picker:** screen 1 shows 10-20 curated words to pick from; screen 2 shows another 10-20 words. The app builds `Word1` + random number + `Word2` (for example "Swift42Otter"). A shuffle button shows new word sets. Curate the lists so no combination is inappropriate; the number keeps names unique.
- Avatars from a set of built-in illustrations.
- **Themes:** per-profile theme picker: dark, light, high contrast, and several accent palettes. Theme tokens drive every color in the app.
- No chat, no messaging, no user-generated text anywhere.
- Parent dashboard: see each player's progress, toggle leaderboard visibility per player, export all data, delete all data (one click, real deletion).
- Cloud sync across devices: solves are append-only with client-generated UUIDs; settings are last-write-wins.
- Plain-language privacy policy and terms pages (placeholder text clearly marked for legal review).

### 5.10 Achievements (`achievements`)

Data-driven JSON rules evaluated by the client (instant celebration) and the server (authoritative). At minimum:

- Firsts: first scan, first guided solve, first unguided solve, first timed solve, first solve with each method (Beginner, 2-Look CFOP, Full CFOP, Roux, ZZ), first pattern, first custom-color cube profile, first ao5, first ao12, first rescan that caught a mistake.
- Time milestones (unguided timed solves): first under 5:00, 3:00, 2:00, 1:00, 0:45, 0:30, 0:20.
- Volume: 10, 50, 100, 500, 1000 solves.
- Learning: notation lesson, each method course, all 2-look OLL/PLL learned (trainer accuracy threshold), full PLL, full OLL, 10 "Next move?" answers right in a row.
- Patterns: each pattern made, all patterns made.
- Improvement: new PB single, new PB ao5.
- Community: entered a weekly challenge.

Tone: celebrate, never shame. No streak-loss guilt; streaks, if any, are opt-in. Unlocks get a polished animation and sound (mutable).

### 5.11 Leaderboards

Purpose: let players see how they compare with themselves and others. Keep it friendly and simple.

- Categories: **Guided** and **Unguided**, by method if the player tagged one.
- Scopes: personal history, Family (players under the same parent), global, and weekly. Optional Friends via parent-approved invite codes.
- **Weekly Challenge:** everyone gets the same 5 server-issued scrambles each week, ranked by ao5.
- **Trust model (document this honestly in the Guide):** times are submitted by the player's browser, so this is an honor-system leaderboard. Lightweight server-side guards only: reject times below a configurable floor, rate-limit submissions, require server-issued scramble IDs for the Weekly Challenge, let parents report entries, and let the admin hide entries from the PocketBase admin UI.

### 5.12 Built-in Guide (documentation)

- Markdown source in `docs/guide/`, rendered inside the app, searchable, and available offline.
- Covers every feature, setting, and stat in plain language: what ao5 means and why the best and worst are dropped, inspection, +2 and DNF, sessions, phases, scrambles, every method and stage, notation, the grip and scan technique, calibration, marking mode, rescans, the Coach's rules, achievements, privacy, and a glossary.
- **Keep the main UI clean:** no paragraphs of explanation in the UI. Every feature title, settings label, and stat name is clickable and opens its Guide entry.
- CI check: every feature ID and settings key has a matching Guide anchor.

### 5.13 Design and UX

- Sleek, modern, dark-first. Glassy panels over the camera feed, bold typography, generous spacing, smooth 60 fps 3D. The cube is the hero element.
- Big touch targets and simple words. A "Grown-up mode" toggle reveals notation, deeper stats, and advanced settings.
- Sound: subtle ticks, a celebration on solve. All mutable.
- First-run onboarding: 3 screens max (privacy note, grip lesson, scan), then straight into using the app. A "skip, use the virtual cube" path is always available.

### 5.14 Accessibility

- **Color-blind support is essential in a color puzzle app:** optional letter or symbol overlays on every sticker (on screen and in scan review), plus color-blind-safe UI accents in every theme.
- Full keyboard navigation, visible focus, screen-reader labels, text for every audio cue, `prefers-reduced-motion` honored, WCAG 2.2 AA contrast in every theme.

### 5.15 Offline and PWA

- Installable PWA with a service worker. The timer, virtual cube, solvers, patterns, Learning Center, and Guide work fully offline. Solves queue for sync when back online.

## 7. Data model (starting point; refine in PLAN.md)

PocketBase collections (full mode). Local-only mode mirrors these in IndexedDB.

- `users` (parents): auth fields only.
- `players`: parent (relation), display name parts (word1, number, word2), avatar ID, theme, settings JSON, leaderboard_visible.
- `cube_profiles`: player, name, 6 colors (OKLab) with user-given names, face mapping, marked color (nullable).
- `camera_calibrations`: stored locally only (per device), not synced.
- `sessions`: player, name, created.
- `solves`: player, session, client UUID, time_ms, penalty, scramble, scramble_id (nullable), method, guided (bool), phase_splits JSON, created.
- `learning_progress`: player, lesson ID, status, stats JSON.
- `drill_results` and `trainer_results`: player, case or drill ID, time_ms, success, created.
- `achievement_defs`: rule JSON (seeded from `packages/achievements`).
- `achievements_earned`: player, achievement, earned_at, solve (nullable).
- `scrambles_issued`: ID, scramble, week, issued_at.
- `weekly_challenges`: week, 5 scramble IDs.
- `reports`: reporter (parent), solve, reason enum.

API rules: players are readable and writable only by their parent; leaderboard views expose only display name, avatar, and times.

## 8. Testing strategy

- **cube-core:** property tests: move then inverse is identity; random sequences keep the cube valid; facelet/cubie round-trips; orientation detection for all 24 orientations; point-of-view transform correctness.
- **algs:** every algorithm, pattern, and practice position verified by simulation (Working Rules 6 and 7). CI fails on any mismatch.
- **solvers:** for 1,000 random-state scrambles per method, the solution solves the cube, stage boundaries are correct, and the time budget holds. Same for pattern goals. Stage detection tested against generated states.
- **rescan logic:** simulated scenarios for on-track, ahead, behind, single-move mistake, and unrelated state.
- **vision:** fixture photos and short videos of the grip-and-spin scan under varied lighting (daylight, warm bulb, dim room, glare), with at least two non-standard color schemes and one marked-sticker cube. Track classification accuracy as a CI metric. Include a script so I can easily add fixtures recorded in my studio lighting.
- **calibration:** fixture videos with normal and flipped feeds.
- **e2e:** Playwright with Chromium's fake camera fed by fixture videos (`--use-file-for-fake-video-capture`): scan, follow, rescan, timer, Learning Center drill, sign-in.
- **Performance:** a benchmark page measuring vision Hz, solver latency, and render fps; document results on a low-end device.

## 9. Deployment

- **Local-only mode:** `npm run build` produces a static site that runs with no backend. Document free hosting on GitHub Pages and Cloudflare Pages, including custom-domain setup, so anyone can host their own copy on their own domain.
